# Folding Search into Control

This plan finishes what *Screen Search and Control* started: it removes `search_screen` as a separate tool and moves retrieval **inside** the `control_screen` script, so one composed program both perceives and acts. The directive is complete replacement, no backward compatibility. The motivation is a specific failure mode of the two-tool split. Today the model calls `search_screen`, its ranked hits land in the conversation as text, and it then writes a `control_screen` script that acts on the ids it saw. Merging the two is what Daisy's one-program thesis wants — fewer round trips, loops and branches over live elements, `evaluate` alongside the search that found the endpoint — but a naive `search()` returning a list invites `click(search(...)[0])`, and in a single-shot script that `[0]` is not laziness, it is structural: the results do not exist when the index is written, so any index is a blind guess. The design below keeps the merge's efficiency while re-encoding, in the primitives' contract, the one safety property the tool boundary gave for free — that you cannot act on a perception you never surfaced.

## Where we are today

`search_screen` and `control_screen` are two tools sharing the `Surface` abstraction (`daisy/computer/surface.py`), retrieval (`daisy/computer/retrieval.py`), and the killable script sandbox (`daisy/computer/control.py`, `control_child.py`). `search_screen` reads the live surface into ranked documents and returns the top hits with their native ids; `control_screen` runs a Python script of bare-name primitives (`click`, `type`, `evaluate`, …) over those ids. The script itself cannot search — the `control_screen` docstring says so outright — so anything that only appears after an action forces the model to end its turn, call `search_screen` again, and start a new script. `search_screen` also hosts the observe-pixels path through its `screenshot=True` flag, which routes a PNG onto the `model_image` side channel. Danger is already handled the way bash handles it: every tool call carries a model-declared `risk` and a `justification`, and `_classify_permission` (`daisy/core/agent_permissions.py`) fuses those with a static read-only assessment into an auto-approve-or-escalate decision that fails safe to escalation.

## The design

**Retrieval becomes two in-script primitives, `find_many` and `find_one`.** Both take a plain-language query and rank the current surface with the existing model2vec + BM25 fusion; both return the same structured hit shape the tool already produces — `{id, name, role, text, state, context}`. `find_many(query, limit=8, all=False)` returns the ranked set and is for observing or harvesting, where the model acts on *every* result and positional iteration is correct because it is not guessing *which one*. `find_one(query, **filters)` is for acting: it returns the single best match, and it is the primitive the model reaches for when a mutating action needs a target. The paired naming is deliberate — cardinality is the salient axis at the call site, and cardinality is exactly the safety distinction, so `find_one` versus `find_many` teaches the contract for free. Both are ranked-by-meaning, not exact string lookups; the docstring says so, because "find" can otherwise be misread as an exact match. The docstring must also nudge the model toward **explicit, descriptive queries** rather than terse keywords — naming the target, its role, and its surrounding context — because a short query spreads probability across every similar control and is what pushes `find_one` into an `AmbiguousMatch` raise or a wrong top hit, so query quality does the disambiguation up front instead of leaving it to the tripwire. This is generic behavioral guidance, not a catalogue of worked examples: the model is capable of applying the principle on its own, and the docstring should state the behavior it wants and stop there rather than enumerating phrasings.

**`find_one` returns the top hit, and raises only when the head of the ranking is genuinely ambiguous.** Uniqueness by count is meaningless over a similarity search — every element has nonzero similarity to any query, so there is never "one match" — and an absolute score threshold is unusable because reciprocal-rank-fusion scores are not calibrated confidences. So `find_one` defaults to the top hit and detects ambiguity structurally instead. A hit is *score-competitive* with the top hit when its fused score is at least 90% of the top hit's, counted only among the top five results. `find_one` raises `AmbiguousMatch` when any score-competitive hit is indistinguishable from the top hit by the triple `(name, role, context)`; otherwise it returns the top hit. Because RRF scores compress hard at the head — adjacent ranks sit within a couple of percent of each other — the 90% band is deliberately generous, and the real gate is the `(name, role, context)` identity test: the percentage only bounds how far down the ranking a twin still counts. This targets the one case where the top hit is a coin flip (twenty identically-labelled "Add to Cart" buttons that even the `context` field cannot separate) and lets the ranking stand everywhere else, including where the top two are distinct but close. There is no positional `which=` escape: the model picks the top hit, and when it is genuinely confused it re-queries with a discriminator, which is what the raise nudges it to do.

**`AmbiguousMatch` carries the candidates and nudges, via the message loader.** The exception text is rendered through `message_loader("control")` over a new `messages/control/ambiguous_match.md`, with variable substitution for the query and the top candidates (each `id`, `name`, `role`, `context`) — the same templating the surfaces already use for messages like `not_connected`. The model reads the competing candidates in the error itself and disambiguates without a second blind read, either by adding a `role`/`name`/`context` filter to `find_one` or by acting on an id it now recognises.

**Mutating verbs accept a query or an id; reads stay permissive.** `click`, `type`, `choose`, `upload`, and `drag` may take either a native id (the model already surfaced it from a `find_*` and chose it) or a query string, which they resolve through `find_one` semantics — top hit, or `AmbiguousMatch`. The read and navigation primitives — `read`, `hover`, `scroll` — resolve to the top hit silently, because a wrong read is self-correcting and non-mutating. This is the whole ambiguity guard, and it is orthogonal to danger: an action can be perfectly unambiguous and still be destructive, or ambiguous and harmless.

**Every action echoes what it touched back to the model.** The `control_screen` result gains an ordered *acted-on* list: one structured record per mutating primitive that ran, in the same `{id, name, role, context}` shape the `find_*` primitives return, tagged with the action taken — "clicked", "typed into", "chose in". The model composes a script blind to the live surface, so without this it learns only that the script ran; with it, it learns it clicked *this* and typed into *that*, and can catch a wrong target on the next turn.

**Danger stays at the tool call, exactly like bash.** The merge does not add a per-primitive risk flag. The whole `control_screen` call carries its model-declared `risk` and `justification`, and those feed `_classify_permission` alongside a static read-only-versus-mutating assessment of the script — the analogue of bash's `read_only_assessment`, computed by scanning which primitives the script calls: a script that only calls `find_*`, `read`, `hover`, or `scroll` is read-only, and any `click`, `type`, `choose`, `upload`, or `drag` makes it mutating. The classifier's existing behaviour carries the rest, including its fail-safe escalation on any doubt. The accepted trade-off is granularity: one approval covers the whole script, so a program that bundles several state changes is gated once, up front.

**`search_screen` is removed, and Enter is a prompt nudge.** The tool, its registration in `daisy/core/agent.py`, and `_tool_search_screen` in `daisy/core/agent_tools.py` are deleted; the canonical read path is now in-script `find_*`, with no compatibility shim. The `control_screen` docstring drops the "the script cannot search" line and gains `find_one`/`find_many`. The guidance in `daisy/core/prompts/computer_control_guidance.md` is rewritten around the new rhythm — one program that finds, disambiguates by content, and acts — and states plainly that a fresh `find_many` result must not be indexed for a state change; use `find_one` or add a discriminator. Submission stays a nudge, not a protocol: the guidance explains that `press("Enter")` and `type(submit=True)` post, and trusts the model to be deliberate rather than gating on a detected-submit signal.

## Decided tradeoffs and deferred work

Two questions that shaped the design were settled deliberately. Ambiguity and danger are kept as separate axes: `find_one`'s `AmbiguousMatch` answers "is the target unclear" and raises into the script for the model to resolve, while `_classify_permission` answers "is the action consequential" and escalates to a human — fusing them would conflate a retrieval problem with a permission one. And detection of destructive actions is intentionally not built: it reduces to a semantic judgment about the target element that no regex or keyword list generalises across labels, languages, and unlabelled icons, so the plan leans on the model's own `risk`/`justification` plus the classifier's escalate-on-doubt rather than a brittle universal detector.

The screenshot path is deferred to its own plan, connected to this one. Removing `search_screen` orphans the `screenshot=True` observe path, and the intended replacement is not a straight port: rather than a raw image on the `model_image` side channel, the direction is a built-in primitive that returns *structured* data compatible with the rest of the `find_*` surface — an OCR/structured read of a drawn surface that has no accessibility tree or DOM — so that a canvas, a map, or a custom-rendered app yields the same ranked, addressable element shape as everything else. That needs its own model choice, CPU-cost budget, and integration design, and will be planned separately.
