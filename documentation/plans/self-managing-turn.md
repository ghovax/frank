# A Self-Managing, Unblocked Turn

This is a behavior plan, not a refactor. The harness works, but it governs the agent with a wall of fixed numbers — a per-turn tool-call ceiling, a goal-continuation counter, a delegation-depth cap, fixed sync/background timeouts — each an artificial limit that stops the agent on a *count* rather than on reality. That contradicts the harness's own intent: a self-managing agent that runs until it is genuinely done or genuinely stuck, and is never blocked waiting on slow work. This plan removes the artificial (agency) limits, replaces the one that truly needs a backstop — the iteration ceiling — with **progress detection**, makes unbounded turns viable by turning on the smart compaction that already exists, gives the agent's **goal and task state durable persistence** so a restart never erases its objective, and moves the sync-vs-background decision out of fixed constants and into the model plus a uniform tool contract. Physical, security, and protocol constants stay — they are not agency limits — but get relabeled so they stop reading as removable policy. It builds on [`typed-turn-core.md`](./typed-turn-core.md) (which made `execute()`/`stream()` thin drivers and `_execute_tool()` a dispatch over per-tool handlers — the seams this plan edits) and the persistence model in [`unified-durable-turn.md`](./unified-durable-turn.md).

## Where we are today

Four different things wear the word "limit," and only the first is what we are removing.

**1. Agency limits — remove.** `AgentRuntime._GOAL_CONTINUATION_LIMIT = 8`, `AgentConfiguration.maximum_iterations = 256` / `_AGENT_MAXIMUM_ITERATIONS = 512`, and `GlobalConfiguration.maximum_delegation_depth = 8`. These stop the agent on a count even when it is making progress. A turn that hits `maximum_iterations` dies with a canned "reached the tool-call limit" one call short of done. This is the contradiction.

**2. Blocking timeouts — already mostly solved; unify.** `BASH_SYNC_CEILING_SECONDS`, `WEB_SEARCH_SYNC_CEILING_SECONDS`, `_MCP_CONNECT_TIMEOUT_SECONDS`, the Playwright/AX timeouts. The problem was never the number but that a slow op *blocks the turn*. The machinery to not block already exists (below); the work is to make every slow tool use it uniformly and let the model own the sync/background decision.

**3. Physical / security / protocol values — keep.** Context-window token budgets (`OUTPUT_TOKENS`, `READ_WINDOW_TOKENS`, `FETCH_TOKENS`, `MAXIMUM_INLINE_IMAGE_BYTES`), signed-URL TTLs (`DEFAULT_URL_TTL_SECONDS`), transfer/payload caps (`DEFAULT_MAXIMUM_FILE_BYTES`), the annotation coordinate grid (`_COORDINATE_GRID_MAXIMUM = 999`), OS input pacing (`CLICK_INTERVAL_SECONDS`, `DRAG_STEPS`, `TYPE_CHUNK_SIZE`). A finite context window, an expiring URL, and the milliseconds the OS needs for a synthesized click are facts, not fences. Removing them breaks correctness or security; they are out of scope except for relabeling.

**4. Detection heuristics — the pattern we want more of.** `surface._no_effect` / `NO_EFFECT_LIMIT` (stop blind actions after consecutive no-ops), `settle()` (poll until a surface stops changing instead of sleeping a fixed guess), `_WHOLESALE_APPEARED_FRACTION`. These already *detect a condition* rather than count. The new progress detector is this pattern lifted to the turn loop.

What already exists that this plan leans on: **`BackgroundJobs`** (`core/background.py`) is a general background-execution runner — `spawn`, `settle_inline(id, timeout)` (run a job, wait up to `timeout` inline, return its result if it finishes, else leave it backgrounded), `drain_completed`, `wait_for_completion`, `request_background`, cancellation, and the resume-pump inject-and-wake path that delivers a completed job into the conversation and wakes the agent. Bash and `web_search` already run through `settle_inline`; **spawn_agent is already non-blocking**; reads/writes already run inline. **Observational-memory compaction** (`CompactionConfiguration` + the Observer/Reflector in `agent.py`) folds older conversation turns into a dense, timestamped observation log and condenses that log when it grows; it is built and correct, and simply **off by default** (`auto = False`). And the **thin turn seams** from `typed-turn-core.md` — `stream()`'s extracted phases (`_finalize_no_tool_calls`, `_run_tool_batch`, …) and the `_TOOL_HANDLERS` dispatch — are where the edits land.

Two genuine gaps, both closed here. **No turn-level progress detector:** the only backstop against a runaway loop today is `maximum_iterations`; remove it without a replacement and a stuck model loops until it exhausts the provider. **No durable goal/task state:** `_active_goal` and the agent's task list (each entry `{identifier, description, status, dependencies}`) are in-memory only. The task store persists the conversation checkpoint, task head/history/artifacts, and background jobs — but not the agent's goal or task list. On the ephemeral-container restarts this deployment does, a long autonomous run silently loses its objective. They are safe from *compaction* (they are not in `self._conversation`), but they are not safe from a *restart*.

## The design

### Progress detection (replaces the iteration ceiling)

A per-turn detector answers "is this turn still advancing, or spinning?" — the loop runs unbounded and stops only when genuinely stuck, never on a count. A turn is **advancing** if an iteration produces any of: a new distinct tool call (by name + arguments), a changed tool result for a repeated call, new assistant text or thinking, or an observable state change (a file written, new information folded in). It is **spinning** if `K` consecutive iterations produce none of those — the same call(s) with the same result(s) and no new assistant content. `K` is small (≈3); it is a *no-progress* count, not an agency cap, so it can only fire when nothing is happening, never on a productive turn. On spin, the turn ends with a distinct `stuck` stop reason (not the old generic "maximum_iterations"), so the transcript reads honestly and the model can be re-prompted. Mechanically, `stream()`'s `while self._calls_this_turn < effective_maximum_iterations:` becomes `while not detector.stuck:`, modeled on the existing `surface._no_effect` / `settle()` patterns. This detector is the **sole** runaway guard once budgets are off (see tradeoffs), so it is built and exercised first, before the caps it replaces are removed.

### Remove the agency limits

Delete `_GOAL_CONTINUATION_LIMIT` (the goal self-nudge just continues; the model decides when the goal is met), `maximum_iterations` / `_AGENT_MAXIMUM_ITERATIONS` (→ progress detector), and `maximum_delegation_depth` (each spawned agent runs its own turn loop with its own detector, so a spinning delegated agent self-terminates; genuine deep recursion that keeps producing new deliverables is legitimate). Remove the `goal_continuation` nudge scaffolding and the dead constants.

### Smart compaction on by default

Flip `CompactionConfiguration.auto` to `True`. This is what makes an unbounded turn viable: context can no longer overflow the window, so there is no wall to hit and therefore no need for a resource budget. Verify the Observer/Reflector behaves under a long, tool-heavy turn (it fires mid-turn at `_should_compact`; the Observer and Reflector are themselves model calls, so compaction is not free — acceptable and expected).

### Durable goal & task state

Goal and tasks become first-class **session-scoped durable state**, mirroring the conversation checkpoint. A new context-keyed store surface on `AppendOnlyTaskStore` — `save_session_state(context_id, goal, tasks)` / `load_session_state(context_id)` — is backed by a small `session_state` table (`context_id` primary key, `goal` text, `tasks` JSON text, `updated_at`). The state is **saved on mutation** (`_tool_update_goal`, `_tool_set_tasks`, `_tool_update_tasks`, and any task-list mutation persist the new state) and **restored on rehydrate** (in `_runtime_for`, right where `load_checkpoint` restores the conversation, `load_session_state` restores the goal and task list into the rebuilt runtime). This makes the "goals and tasks must never be wiped" requirement hold against **both** compaction (already true — they are separate from `self._conversation`) **and** restart (new); an invariant test locks that compaction never folds them and that a restart round-trips them. The task element type is renamed from `TodoTask` to `TaskItem` while it is being made durable — the old name doubled "todo" and "task" for one concept, and the new name reads cleanly against the persisted schema without colliding with the A2A `Task` or the permission `_ToolPlan`.

### The sync / async tool model

One uniform contract over the existing `settle_inline`: every potentially-slow tool runs a job and waits up to a **default wait window** inline, and the model overrides that per call — the "default" that makes a tool feel sync or background is just the size of the window. **Bash is sync by default:** its params are `timeout` (always present, sane default, model-overridable — the max it will run) and `background: bool = false` (fire-and-forget); the default blocks up to `timeout` and returns the real output, and on `timeout` exceed it **auto-backgrounds as a non-destructive safety net** (returning "still running, moved to background, here is the handle") rather than killing a long build the model forgot to flag, while `background: true` skips the wait entirely. **Expectedly-slow tools background by default** — `fetch_url`, `download_file`, `call_mcp_tool` get a short default wait window, so a near-instant call still returns inline and a slow one backgrounds and delivers via inject-and-wake, each overridable to sync (`web_search` already behaves this way). **Interactive tools are sync but backgroundable** — `computer` / `browser` self-settle, so an action returns promptly. **Reads and writes are always sync** — `read_file`, `edit_file`, `write_file` are fast, local, and deterministic, and the model needs the result immediately. **`spawn_agent` / `call_remote_agent` are already async** and unchanged. The per-tool wait windows replace the fixed `*_SYNC_CEILING_SECONDS` constants; they become the tool contract's defaults, not global policy.

### Constant hygiene (rides along)

As each file above is touched, relabel or relocate its physical, security, and protocol numbers so the code makes obvious which values are physics/security/protocol (kept) versus tunable policy. No separate phase and no behavior change — just naming, so a future reader does not mistake a URL TTL or a coordinate grid for a removable fence.

## What stays, and why

The physical/security/protocol/geometry constants of §Where-we-are #3 stay. They are the shadow of real constraints (a finite window, an expiring signed URL, a wire payload cap, a coordinate space, OS event timing). Making the *context* budgets derive from the live window already happens in `tuning.py`; deriving inline-image/file caps from live provider limits is a possible later refinement, but it is not agency and is out of scope here.

## Build order

Two phases, each independently shippable and revertible.

1. **The unblocked turn** *(all behavior; verified live, together).* Build the progress detector; delete the three agency caps and the goal-nudge scaffolding; turn compaction on by default; add durable goal/task persistence with save-on-mutation and restore-on-rehydrate (and the `TodoTask` → `TaskItem` rename); lock the goal/task invariant. These are one coherent behavior — an unbounded turn that stops only when done or stuck, whose context cannot overflow and whose objective survives a restart — and cannot be landed piecemeal (removing `maximum_iterations` requires the detector; the unbounded turn requires compaction-on to be viable).

2. **The sync/async tool model** *(behavior; on `BackgroundJobs`/`settle_inline`).* Bash sync-default + `timeout` + `background`, auto-background on timeout-exceed; slow tools background-by-default; interactive tools sync-but-backgroundable; reads/writes sync; spawn unchanged. Relabel the touched timeout constants.

## Testing

This changes runtime behavior by design, so the bar is observed behavior, not "provably identical." Driven through the fake-LLM turn harness plus targeted live runs: a turn that legitimately needs hundreds of tool rounds now completes instead of dying at 256; a deliberate no-progress loop is caught by the detector in ~`K` rounds, not hundreds; compaction fires mid-turn on a long run and the goal/task state is untouched, and a simulated restart round-trips goal + tasks from the DB; bash returns a fast command inline, auto-backgrounds one past `timeout` and later delivers it, and returns a handle immediately under `background: true`; a slow `fetch_url` backgrounds and delivers while a fast one returns inline, and reads/writes stay sync.

## Decided tradeoffs

**Unbounded cost, accepted.** With resource budgets dropped and compaction handling context, the progress detector is the *only* guard against a subtly-productive infinite loop burning spend. This is a deliberate choice for a self-managing harness; it puts the weight on the detector being trustworthy, which is why it is built and tested first. **Compaction is lossy but never erases intent.** A marathon run folds old turns into observations and loses specifics — acceptable for "keep going" — but goal and task state are dedicated, now-durable state that compaction structurally cannot touch. **Timeout-exceed auto-backgrounds rather than kills** — non-destructive, so a long build the model forgot to flag is preserved, not lost (reversible to hard-kill if strict determinism is later preferred).

## Implementation status (as built)

Both phases landed and are verified against the fake-LLM turn harness (the executor + DefaultRequestHandler + AppendOnlyTaskStore driven with only the model faked; the harness is not committed, per the repo's no-committed-tests convention). The recommended choices made for the gaps the plan left open:

- **Progress detector (`_TurnProgress` in `core/agent.py`).** It remembers the set of distinct tool-call signatures (name + canonicalized arguments) the turn has issued; a round that introduces at least one new signature resets the streak, and a round that only repeats already-seen signatures — or a malformed-call retry that issues none — advances it. The turn is `stuck` at a streak of `_STUCK_THRESHOLD = 3`, ending with a `stuck` stop reason. This catches exact repeats, N-cycles (once the cycle's distinct signatures are all seen), and a wedged malformed-call loop, while a genuinely productive turn (any new action each round) runs unbounded. `stream()`'s `while self._calls_this_turn < maximum_iterations` became `while True` with the detector as the only stop.
- **Goal nudge → nudge-once-per-stop, no counter.** `_GOAL_CONTINUATION_LIMIT` is gone. When the model stops (no tool calls) with an active goal, it is nudged once to reconsider; if it produces no tool calls again it has reaffirmed done and the turn completes. Any tool call clears the flag, so a model that keeps working is nudged fresh each time it next stops — unbounded continuation while it acts, clean completion when it settles, and no re-prompt loop.
- **Delegation depth cap removed entirely.** A spawned agent runs its own turn loop with its own progress detector, so a recursion that stops producing new work self-terminates. The residual — a deliberately recursive fork that keeps producing *new* spawn calls — is bounded only by the accepted unbounded-cost tradeoff, not by a depth number; a concurrent-agent *resource* guard (not an agency count) is the principled future safety net if that ever bites, consistent with the "resource, not agency" line this plan draws.
- **Durable goal/tasks.** `TaskItem` (renamed from `TodoTask`) and the goal persist to a new `session_state` table via `save_session_state`/`load_session_state`, saved **on mutation** (a dirty flag set by `set_tasks`/`update_tasks`/`update_goal`, persisted at the next checkpoint alongside the conversation) and restored in `_runtime_for` when a context is rebuilt cold. `delete_context` drops the row too. Structurally immune to compaction (they are not in `self._conversation`) and now to restart.
- **Store concurrency fix (bonus, required for the above to be reliable).** The durable-state writes exposed a pre-existing race: `save()` derived each history row's `seq` from a cached `_persisted_count` that desyncs from the DB across the terminal-compaction rewrite, so two concurrent saves could compute the same `seq` and collide on the unique `(task_id, seq)` constraint. The cache is removed; `_history_count` now reads the authoritative `MAX(seq) + 1` inside the write transaction. This made the full harness deterministic (was ~1-in-6 flaky before, on unrelated pre-existing runs).
- **Sync/async tool model.** Bash is sync by default with a per-call `timeout` (auto-backgrounds on exceed, never kills) and an explicit `background`. `fetch_url` and `download_file` — silent blocking network ops — background by default via a short `settle_inline` window (`_run_backgroundable_tool`): a fast call returns inline, a slow one backgrounds and delivers via the resume pump. `call_mcp_tool` is left synchronous **because it already streams live `McpEvent` progress** — backgrounding it would remove that feedback, so it is not a blocking-silently tool. `computer`/`browser` stay sync (they self-settle), reads/writes stay sync, and `spawn_agent` was already async. The fixed `*_SYNC_CEILING_SECONDS` tuning limits are replaced by per-tool default windows.
