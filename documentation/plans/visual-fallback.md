# Removing Computer-Use Screenshots, and a Deferred Visual Fallback

This plan is deliberately incomplete, and says so up front. It lands one concrete change now — it rips the live-surface screenshot path out of computer use — and it *sketches, without settling,* the structured visual fallback that should eventually replace it. Vision is worth doing, but doing it well needs far more planning than the discussion behind this document has produced, and shipping a half-built pixel capability is worse than a clean, documented gap. The removal is a companion to *Folding Search into Control*, which already deletes `search_screen` — the tool that hosted the `screenshot=True` flag — so this plan completes that removal by taking out the pixel producers and the permission underneath, and it records exactly how a real visual tier should be reintegrated later so the gap is a marked path forward rather than lost context.

## What lands now: the screenshot capture path comes out

The current screenshot capability is observe-only and low-value: it captures a window (native) or the page (browser) to a PNG and rides the pixels onto the model's vision side channel for the model to *look at*, never to act on. It is the acknowledged last resort — `capture.py`'s own docstring calls it "the least accurate option, used only when there's no structure to read" — and *Folding Search into Control* removes its only entry point when it deletes `search_screen`. Rather than leave the producing machinery stranded behind a deleted flag, this plan removes it: `computer/capture.py` (the CGWindow grab) in whole; the `screenshot()` method on both surfaces (`computer/engine.py`, `computer/web.py`) and engine's `capture` import; the Screen Recording permission that exists solely to gate it (`screen_recording_granted` / `request_screen_recording` / `open_screen_recording_settings` in `computer/permissions.py`, its use in `engine.py`, and its surfacing in `server/routes/settings.py`); the tool-handler wiring (`_screenshot_extra` in `agent_tools.py`, `_screenshot_data_uri` in `agent_internals.py`, and the `screenshot` parameter on `search_screen` in `tools.py`); and the model-facing prose and messages that describe it (the screenshot passages in `computer_control_guidance.md`, and the `screen_recording_needed` / `screenshot_observe_only` message templates). The result is a surface that reads structure and acts on it, with no pixel path at all until the visual tier below is built.

## What is not removed

This is the removal of *live-surface pixel capture for computer use*, not of image capabilities. `read_file` still ingests image files natively and attaches their pixels for vision models (`read_image_file` and the image MIME handling in `tools/file_tools.py`), the `model_image` side channel that carries those pixels is untouched, and the artifacts panel still renders images. The screenshot helpers being deleted (`_screenshot_data_uri`, `_screenshot_extra`) are confirmed screenshot-only and share nothing with `read_file`'s image path, so removing them leaves the general image surface intact. The line is precise: the harness loses its ability to photograph a live app or page for computer use, and keeps every other way it already sees images.

## Deferred: the visual fallback

Everything in this section is direction, not decision, and each piece needs its own planning pass before it is built. When a surface is drawn rather than structured — a canvas, WebGL, a custom renderer, an app that refuses the accessibility handshake — the intended replacement is not the old raw screenshot but a structured read that folds into the `find_*` primitives from *Folding Search into Control*. The shape settled tentatively in discussion is: detect the need **by coverage**, extending `_is_incomplete` (native) and a browser canvas/WebGL check into a measure of how much of the viewport is unstructured, so an OCR/detection pass fires only over the drawn region and only when structure is genuinely absent — no model decision, and the cost is gated to the cases that need it. Visual elements are folded into `find_*` **transparently**, in the same hit shape as tree elements, so the model never learns a result came from pixels. Acting on one goes through a **centroid-behind-an-id**: the element carries a bounding box, its action point is the box centroid, and the model targets the opaque id exactly as it does a tree element, so coordinates never surface; the click is synthesized point input through the plumbing that already exists (`input_synthesis` on native, Playwright mouse on the browser), which means it loses the actionability guarantees the trusted layer gives structured elements. Provenance is disclosed **reactively, not proactively**: visual ids have no re-resolution, so they are invalidated on any surface-changing action, and the only moment "visual" leaks to the model is a broken action — a stale id raises an error telling it to find again — with the acted-on echo from the previous plan (which reports each action's target by its text) carrying the silent-wrong case instead of a provenance tag. Deduplication is genuinely unsettled: because the same label can be read once from the tree and once from OCR, and two indistinguishable score-competitive hits would trip `find_one`'s `AmbiguousMatch` on what is actually one element, some dedup is required, and the leading options are region-scoped OCR (mask the structured boxes, OCR only the gaps — dedup by construction) versus an IoU post-filter (OCR everything, drop visual hits overlapping a tree box) — undecided.

These weaknesses are on the record and must survive into whatever plan finishes this: synthesized point input has no visibility/occlusion/scroll-into-view check; mapping detector boxes from image space to screen or viewport space (device-pixel-ratio, capture scale, surface origin) is the classic screenshot-agent bug and the primary implementation risk; a box centroid misses on irregular or occluded shapes; visual ids are valid only within their snapshot with no rebind; and reactive disclosure catches *breaking* failures but not a centroid that lands slightly off yet still clicks, which rides on the acted-on echo and model self-correction.

## How to reintegrate

The seams are left where a future implementer can find them. Detection attaches where `_is_incomplete` already lives in `engine.py`, extended with the browser coverage check. The visual read folds into the `find_*` primitives from *Folding Search into Control*, sharing their id space and hit shape. The action tier reuses `input_synthesis` (native) and Playwright mouse (browser) for the centroid click. The capture primitives to restore are `page.screenshot` on the browser and a CGWindow grab on native, the latter behind a re-added Screen Recording permission — the same code shape removed above, which is why the removal is documented rather than silent. The model-facing guidance and message templates deleted now are the ones to re-add. In short: this plan removes a dead-end capability and leaves a labelled socket where the real one plugs in.

## Open questions and pointers to future discussion

The visual tier is blocked on decisions this document does not make. The scope of the read is open — text-only OCR (fast, CPU, covers labelled surfaces) versus text plus **interactable-element detection** for unlabelled icons and controls — and the detection model is itself a research pointer: **RF-DETR** (Roboflow's real-time DETR, Apache-2.0, DINOv2 backbone) is worth evaluating for UI-control detection alongside the YOLO-style detector OmniParser uses, as a future-search item rather than a choice made here. The engine and budget are open under the fast-CPU, Apple-Silicon-first constraint set earlier, including whether the vision *reasoning* stays local or the local side does only OCR while the session's main model reasons. The coverage threshold that triggers the read is unset, as is the dedup strategy (region-scoped versus IoU post-filter versus a combination). And surface parity and staleness scope are open — both surfaces at once or browser-first, and invalidate-all-visual-ids-on-mutation versus only on scroll, relayout, or navigation. Each of these is a pointer to a future planning pass, and none should be inferred from this document's tentative sketch.
