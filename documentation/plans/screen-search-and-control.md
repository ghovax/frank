# Screen Search and Control

This plan reworks how the model perceives and drives a computer or browser, and folds the project's search tools into one coherent taxonomy. Today `computer` and `browser` are two tools that expose a live surface as a nested tree the model explores step by step, plus a separate verb for every gesture; search is split across three literal tools and has no semantic path anywhere. The directive was to replace the tree-exploration model with **retrieval** (state a goal in plain words, get the relevant elements back), to let the model **compose** actions in a script instead of calling one pre-made gesture per turn, and to unify the two surfaces behind one abstraction — with no backward compatibility and no effort ceiling. The element-encoding decision at the centre of the retriever was settled by an experiment, not by taste; its numbers are in *Decided tradeoffs*.

## Where we are today

**The two automation tools are a tree the model walks by hand.** `computer` (native macOS accessibility) and `browser` (the user's own Chrome over CDP/Playwright) share the `Surface` base in `daisy/computer/surface.py`, and each exposes the same shape: `observe` returns a capped, nested snapshot; `find` is a *case-insensitive substring* match over an element's name/value/context; `read` pages visible text in windows; and then there is a distinct verb for every physical act — `click`, `type`, `select`, `caret`, `scroll`, `hover`, `choose`, `upload`, `drag`, `press`, plus `evaluate`/`network` on the browser. Every one of those is a full model round-trip: read a snapshot, decide, act, re-read the diff, repeat. A task that touches twenty rows is twenty cycles, each shipping a fresh snapshot into context, and the substring `find` cannot bridge "the checkout button" to a control the page happens to label "Proceed". The large amount of machinery that fights surface churn — settlement polling, stuck-detection, the actionability-error parser, the durable ref registry that survives re-renders — all exists precisely because the model is driving the rendered surface one brittle step at a time.

**Trusted input is the core strength, and the rework must not lose it.** The browser tool's whole value is that it acts *as the user*: Playwright runs its actionability pipeline (is the element visible, enabled, not occluded by an overlay) before every click, scrolls with a real hover-and-wheel gesture routed by the browser's own scroll chaining, and handles native file-choosers and `<select>` menus — all carrying `isTrusted`, which many sites check. The native tool has the analogue in semantic AX actions (`AXPress`/`AXConfirm`/`AXOpen`) tried before any synthesized mouse event. A rework that dropped to page-level `element.click()` or `input.value = "…"` would silently regress exactly the hard cases — an overlay intercepting the click, a file picker that only a trusted event may open, a native dropdown JS cannot drive, a drag, an anti-bot heuristic on synthetic events — so whatever replaces the per-gesture verbs has to keep routing through that trusted layer, not around it.

**Search is fragmented and entirely literal.** `web_search` hits the internet; `find_files` globs filenames; `search_content` greps file bodies. There is no *semantic* retrieval anywhere in the tool surface — not over the codebase, and not over the live screen — even though the accessibility tree already hands us the screen pre-atomised into discrete, individually-addressable elements, which is exactly the corpus a retriever wants.

**Authenticated API control is present in pieces and wired to nothing.** The browser tool already has `evaluate` (run arbitrary JS in the real, signed-in page) and a `network` reader — but `network` records only request *lines* (method, url, status, resource type) with a 100-entry ring and never captures headers or bodies, so the model can see *that* a page fetched `/api/txns` but not what it sent or what came back. The single capability that would let the model pull data straight from a page's own backend, riding the real session, exists in fragments and is exposed to nothing that composes them.

## The design

**One retriever recipe, three corpora, engines chosen for domain fit.** The model states a goal in plain text and a retriever indexes the relevant corpus and returns ranked hits. The recipe throughout is the [semble](https://github.com/MinishLab/semble) stack — model2vec static embeddings for semantic similarity plus BM25 (Okapi) for lexical matches, fused into one score — because it is CPU-only, needs no GPU or API key, indexes in the low hundreds of milliseconds, and answers in ~1.5 ms. It is applied three ways. **`search_code`** uses semble directly: its source confirms it is code-specialised — tree-sitter *code* chunking, the `potion-code-16M` code embedding model, and code-only ranking signals (definition boosts, identifier-stem matching, test/legacy penalties) — and it indexes straight from disk via `SembleIndex.from_path`, with the `previous`/manifest path making re-indexing an unchanged tree near-free, so the repo needs no serialisation. **`search_screen`** deliberately does *not* use semble: a DOM/AX tree is not code, so tree-sitter chunking is meaningless on it and a code model misreads UI labels; instead it reuses the same model2vec + BM25 recipe with a **general, retrieval-tuned** static model (`potion-retrieval-32M`), treats **one element as one document** (the accessibility tree already provides the units, so there is no chunking stage at all), and builds the index **in memory on every turn** — a screen holds a few hundred elements versus a repo's thousands of chunks, so a full re-index is sub-millisecond and writes no temp files. **`search_web`** is the existing web search renamed into the taxonomy. The two screen retrievers return different result shapes (an actionable element handle versus a file-and-line snippet), which is why they are sibling tools rather than one tool with a scope argument.

**The embedding key is the element's own words, and only those.** Each element is reduced to one short document by joining its standardised accessibility text — `name`, then `description`, then `value`, then `context` — with single spaces, dropping empty fields; these are the fields the platform already computes (the ARIA accname/accdescription algorithms and grouping relationships on web; `AXTitle`/`AXDescription`/`AXValue` and the enclosing group on native), so nothing about the string is a format we invented. Concretely, an "Add to Cart" button sitting in the card for a "USB-C Hub — $49.99" becomes the document `Add to Cart USB-C Hub — $49.99`, a password field becomes `New password Change password`, and a toggle becomes `Two-factor authentication on Security`. The element's `role`, its state flags (`disabled`, `selected`, …), its `clickable` bit, and its native handle travel **alongside as structured metadata** on the hit — available to the model and usable as filters — but are kept **out of** the embedded text, because embedding them adds crowding without adding retrieval signal (measured below). An element with no accessible name (an icon-only button) falls back to `role` + `context` for its document and is otherwise reached positionally. `search_screen` returns the **full, untruncated** text of each hit, which is what lets it subsume the old windowed `read`.

**Native handles, obtained natively — never a string-built selector.** A hit carries the platform's own handle: on the web that is the Playwright aria-ref resolved to a live node object (we never assemble an `aria-ref=…` selector string ourselves), and on native it is the real `AXUIElement`, with its tree path kept only as a fallback for rebinding after a re-render. Tabs are keyed by their CDP `targetId` (a stable 32-hex string), and network exchanges by their CDP `requestId`. The friendly-alias registry that used to mint `ref1`/`tab1` handles over these is removed: under a search-then-act flow the model copies an id straight out of a search result into its next call rather than composing it by hand, so the raw native id is what crosses the tool boundary, and its per-snapshot validity is sufficient because the identify→act window is a single step.

**`control_screen` is one tool whose argument is a Python script of bare-name actions.** Acting is a single tool; its main parameter is a Python script (a string), and inside that script the primitives are bound as bare names — `click(id)`, `type(id, text)`, `press(keys)`, `scroll(id, direction)`, `read(id)`, `drag(src, dst)`, `choose(id, option)`, `upload(id, paths)`, `select(id, …)`, `caret(id, …)`, plus web-only `evaluate(js, *args)` and `navigate(url)` — with no `daisy.` prefix and no `control_screen:` wrapper. Targets are the native ids a prior `search_screen` returned. The same primitive names exist on both surfaces and each routes to the **trusted** layer underneath — Playwright/CDP actionability on web, AX actions or synthesized input on native — so the model gains composition (loops, conditionals, one script doing a whole task) without losing the trusted-input guarantees. A worked example of the two-phase flow:

```
search_screen("year dropdown and apply button")
  → [ {id:"e231", role:"combobox", text:"Year Relevance"},
      {id:"e240", role:"button",   text:"Apply"} ]

control_screen(script="""
choose("e231", "2025")          # native <select>; JS .value cannot drive this
click("e240")                   # trusted, actionability-checked click
rows, page = [], 1
while True:                     # pull the page's own API, in-page, real session
    data = evaluate("p => fetch(`/api/txns?year=2025&page=${p}`).then(r => r.json())", page)
    rows += data["items"]
    if not data["hasMore"]: break
    page += 1
return {"exported": len(rows)}
""")
```

**Search and act are two phases, with no `find()` inside the script.** `search_screen` identifies targets and returns ids; the `control_screen` script only *acts* on ids it was handed. Searching mid-script is deliberately not possible — it would blur identify-then-act into an unpredictable interleaving — so an element that only appears after an action (a menu item revealed by opening its menu) is reached by a second search→act cycle, not by re-querying inside the loop. The cost is an extra round-trip for dynamic surfaces; the gain is that a script is always a straight-line sequence of acts on known ids.

**HAR-style control is just the `evaluate` primitive.** Replaying a page's own API from inside the live page — the `evaluate("p => fetch(...)", page)` in the example — rides the real session's cookies, the page's own request-signing JavaScript, and the browser's native TLS fingerprint, which is why an in-page replay succeeds where an out-of-band HTTP client is handed a `403`. There is no separate HAR subsystem and no capture-and-replay machinery: replay is one primitive line in a normal script, and the only JavaScript anywhere in the design is a string payload handed to the browser (exactly as Playwright's `page.evaluate` already takes one), never a second interpreter running beside Python. To *discover* which endpoint to call, the model searches for it explicitly — `search_screen` also indexes and surfaces the page's captured network exchanges, returning the full request and response for a matched one — and the tool description and system prompt state that this capability exists, in the present-tense descriptive voice the rest of the harness uses, so the model knows it is there without being told when to reach for it.

**The script runs in a killable subprocess with an RPC bridge.** `control_screen` executes the model's Python in a short-lived child process; the bound primitives are thin stubs that RPC to the server, which performs the real `Surface` action on its single serial worker thread and returns JSON. A wall-clock timeout kills the child, CPU and memory are bounded by rlimits, and a crash or a runaway loop dies with the child rather than taking the multi-session server down with it. The RPC surface stays tiny precisely because we already decided that element ids and results cross the boundary as strings and JSON, not as live Python or Playwright handles — so a primitive call marshals a name, a few string/JSON arguments, and a JSON result, nothing more. In-process `exec` was rejected here: it is simpler and needs no bridge, but Daisy is a server hosting live sessions and a control script that can hang or crash the whole process is unacceptable, and only a subprocess makes a runaway loop actually killable.

**The tool taxonomy.** The search surface becomes three parallel retrievals over three corpora — `search_web` (the internet), `search_code` (the repo, semble), `search_screen` (the live UI) — plus `control_screen` for acting. `find_files` and `search_content` are removed, because literal name and content search is `bash`'s job (`rg`, `fd`, `find`) and does not warrant dedicated tools. `computer` and `browser` collapse into the `search_screen`/`control_screen` pair. Everything else on the tool surface keeps its already-consistent name.

## Decided tradeoffs

**The encoding was chosen by measurement, not intuition.** On a 31-element labelled surface (a shopping page plus account settings) with 20 gold-target queries, BM25 scored the raw JSON dump, a formatted `{role}: {name} — {context}` template, and the plain words-with-context join *identically* — top-1 0.85, MRR 0.90 — because Okapi's IDF drives the repeated JSON keys, which are 58% of every dumped document, to essentially zero weight; even the two queries I built to collide with the keys `name` and `value` still ranked their gold element first under the JSON encoding. So the lexical "JSON is noise" concern did not hold. But in the mean-pool embedding space (which is faithful to model2vec's actual operation, so the measurement stands even without the true model loaded) that same shared boilerplate collapses documents toward a common centroid: mean inter-document cosine similarity was **0.60 for the JSON dump versus 0.03–0.07 for the clean encodings**, an 8–20× loss of separability that degrades the dense half we run alongside BM25. The largest effect, though, was neither — it was **context**: dropping the computed context field (a strict name-only encoding, or the raw platform snapshot line, both of which omit it) cost **about 13 points of top-1**, because context is what distinguishes five identically-named "Add to Cart" buttons and two "Remove" buttons from one another. Hence the final key — the element's words *including* context, with JSON scaffolding and role kept out. One claim stayed unmeasured: true semantic synonymy of the screen embedder (matching "log in" to a "Sign in" control), because the model host `huggingface.co` is egress-blocked in this build environment; it is validated on the first run that can load the model.

**Trusted input is non-negotiable, which forces the composition language to be Python, not page JS.** Native apps have no JavaScript runtime, and page JS cannot produce trusted input on the web regardless — so the script must run host-side, in Daisy's own language, with primitives that call the trusted layer, and it is then identical across both surfaces. The single JavaScript touchpoint, `evaluate`, is a data payload sent into the browser, is web-only, and exists solely for in-page extraction and authenticated replay.

**No redaction, by explicit opt-in.** The browser tool is opt-in as a whole; within it the model sees network headers, tokens, and bodies verbatim. This is a deliberate product decision — the user authorises the capability when they enable it — and it removes an entire fragile redaction layer that would otherwise have to correctly scrub secrets from every captured exchange.

**Behaviour is described, never enforced.** Tool descriptions and the system prompt explain what each capability *is* and let the model compose freely; no strategy ("prefer the API", "always search before acting") is encoded in a prompt or a tool schema. Composability is the point, and it comes from the primitives being general, not from scripted behaviour.

**No backward compatibility.** The two automation tools, three of the search tool names, the per-gesture verb vocabulary, the ref-alias scheme, and the `computer`/`browser` entry points all change or disappear, because nothing outside the repo depends on them and the whole value is in the cleaner surface.

## Testing

The retriever is gated by the labelled query set scored on top-1 / MRR / Recall@3 per encoding — the same harness that produced the encoding decision above — and the chosen key must hold its margin over the JSON and name-only baselines; it is re-run once the screen embedder can load, to confirm that semantic (synonym) retrieval works and not only lexical overlap. Trusted input is verified on the cases page-JS cannot fake: a file-chooser opens, a native `<select>` changes value, a click through a cookie-banner overlay lands on the intended control, and a drag reorders a list — each driven by a `control_screen` primitive rather than a synthetic event. The sandbox is verified three ways: a script with an infinite loop is killed at the timeout, a script that raises leaves the server healthy, and a normal script's primitive RPC calls return their results in order. Cross-surface parity is one script of the same primitives run against both Chrome and a native app, asserting identical behaviour minus the web-only `evaluate`. The HAR path is an in-page authenticated `fetch` returning JSON from a signed endpoint that an out-of-band client is refused. The taxonomy is verified by `find_files` and `search_content` being gone, the three `search_*` tools and `control_screen` being present, and `computer`/`browser` retired.
