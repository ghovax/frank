Look at and act on the web in the user's own Chrome the way a person does. It connects to their real, running browser — their profile, their logins, their live session — so whatever they are signed into is already there; you never open a separate browser, copy a profile, or move their cursor. It reads a page's own structure (iframes included) and acts inside the page with real actionability checks. Use this for anything on the web; use the `computer` tool for native Mac apps.

**Look with `observe`.** It reads the page's elements, each with a short stable `ref` you act on, plus its role, name, value, and the `context` it sits under — so twenty identical "Add to Cart" buttons are told apart by the product above each. Give it a `query` to search the whole page for what you are after, or an `element` ref to expand just that part (or, with an `offset`, take in its text a window at a time). Big pages are capped — pass a `goal` (what you are trying to reach) and the cap keeps what is relevant. Every acting call re-reads the page and tells you what changed (`changed`, and `url_changed` when the page's state or route has moved), so you rarely observe again just to see an effect; refs stay valid across calls.

**Get around and act.** `navigate` opens a URL (or goes back, forward, or reloads). `pointer` clicks, hovers, or drags an element by its ref. `press` sends a key or shortcut (Enter, Escape, Meta+C, …). `type` enters text; `select` and `caret` choose text and place the cursor by what it says; `scroll` reveals more — aim it at an element to scroll the pane that element lives in, which is how you load more of a feed. `choose` picks an option in a dropdown and `upload` attaches files — the reliable ways to drive those controls.

**When structure is the faster path, take it.** `evaluate` runs JavaScript in the real signed-in page and returns its JSON — the direct way to pull a table, read an endpoint, or compute something, instead of paging through text. `network` shows the requests the page has made — the data behind a rendered view is often the quickest, most accurate thing to read. Both run with the full privileges of the user's session, so use them deliberately.

**Combine these freely, and don't grind.** There is no fixed procedure — reach the outcome however fits. When something you do changes nothing, don't repeat it; look again, target a different element, go straight to a URL, or read the data with `evaluate`. If a page draws its own content with nothing to read (a canvas, a map, a WebGL view), take a `screenshot` to see it and tell the user what to do — never guess coordinates and click blind.

A few things are handled for you. JavaScript dialogs are answered automatically and reported; to go through with a confirm, pass `dialog: accept` on the action that triggers it. `tabs` lists, opens, switches, and closes tabs — prefer opening a new one for fresh work so the user's current tab is left alone. And if the browser connection isn't turned on, the tool tells you the one-time switch for the user to enable — relay it plainly and stop, rather than retrying.

One boundary worth keeping straight: this tool *does things* on the real web (check mail, use an account, fill a form) and is the default for any real web task; the artifacts panel (the `open_artifact` tool) only *previews* something to look at, so "open it on the side" or "show it as an artifact" means that panel, not this. If a request could genuinely go either way, ask which they want.
