# Find, Analyze, and Read Scholarly Papers

You are the driver of this skill. The engine is the **`scholar` Python package** (in `scripts/scholar/`) — a set of functions you call directly from Python. Every function returns a plain dict, and the records they return carry an `ids` object, so the output of one call is the input to the next. There is no fixed pipeline to follow: compose the functions however the question demands.

**Design model — stateless live composition.** Every query hits the upstream sources (OpenAlex, Semantic Scholar, Crossref, arXiv, PubMed/Europe PMC, Zotero) **fresh**; the package holds no local materialized graph, index, or cache of scholarly metadata between calls. Python is the query language and you are the query planner: relational or "graph-shaped" questions (e.g. an author in a given byline position, multi-hop citation traversal, co-authorship structure) are answered by composing the live-fetching functions and filtering/looping in plain Python, **not** by querying a stored graph. This is deliberate — it keeps every answer grounded in the current upstream state rather than a snapshot that can drift (see "Verify, don't trust stored facts"). The lone persisted store is the user's Zotero library, which is curated state, not a metadata cache; even it is read back live through the Zotero Web API. If a future need calls for genuine graph analytics (deep multi-hop paths, centrality, community detection), the proportionate move is a composed function that materializes only the needed subgraph **transiently** for that one script (e.g. into a `networkx` graph) — not a persistent graph database or a separate query-language layer.

## Calling the functions

Run the package with **`uv run python`** from `scripts/` (the project root): the project is installed editable, so `import scholar` works with no setup and `uv run` supplies every dependency. The invocation is always the same shape — import the package, call whatever functions the task needs, and print what you want to read back:

```bash
uv run python - <<'PY'
import json, scholar
scholar.configure_logging()  # only when you need warnings surfaced to stderr
# Compose the task here: call a scholar function, read the ids and fields off the dict
# it returns, and feed those into the next call -- chaining discovery, analysis, full-text
# retrieval, and Zotero writes in whatever order the question needs, with any plain-Python
# filtering, sorting, or looping in between. Build up whatever you want to report.
print(json.dumps(result, default=str))
PY
```

**Composition is yours to arrange.** Every function returns a dict and every result record carries an `ids` object, so the output of one call is the input to the next: take an id — or an author, a query, a list of papers — from one result and pass it to the next function, in whatever order the question demands. There is no fixed pipeline. Chain as many calls as you like in one script (one process, shared imports); run independent work concurrently by passing a **list** as a function's primary argument (batched fan-out, below) rather than launching separate `uv run` processes; and drop to raw composition in that same script — a custom loop, a hand-built dedup set, or a direct API fetch for a field the functions don't surface (e.g. the OpenAlex `/authors/<id>` record) — whenever the built-in functions don't cover the need. The function reference below and the per-source notes in `references/sources.md` are what you assemble from; how you assemble them is up to you. Call `scholar.configure_logging()` at the top when you need the engine's warnings (see "Report every warning" below); the functions are otherwise silent.

## The functions

Each returns a dict (see the function's own docstring for parameters and return shape). **Every Layer 1–3 function is batch by default**: pass its primary argument (query / paper id / author) as a single value for one result dict, or as a **list** to fan the whole list out across a thread pool and get the results back in input order under `results`, so N calls cost roughly the wall-clock of one. The `zotero_*` functions are likewise batch-first (they take lists and write in chunks of 50, or upload PDFs in parallel).

|---|---|---|
| `search(query, ...)` | find | Topical discovery across all sources, de-duplicated and ranked. Returns `{"meta", "results"}`. |
| `lookup(paper_id)` | analyze | Fetch one paper by id (DOI/arXiv/PMID/PMCID/OpenAlex). |
| `citations(paper_id, direction=..., source=...)` | analyze | Works `citing` a paper, or its `references`. `source="semanticscholar"` adds influential-citation flags and citation contexts. |
| `similar(paper_id, source=...)` | analyze | OpenAlex related works, or the Semantic Scholar recommender (`source="semanticscholar"`). |
| `facets(query, by=...)` | analyze | Counts grouped by year/institution/venue/type/open_access/topic/country. |
| `find_authors(name)` | analyze | Disambiguate a name into candidates with affiliation, metrics, and topics. |
| `coauthors(author)` | analyze | An author's collaborators, each with h-index, citations, and topics. |
| `author_works(author, coauthor=..., maximum_results=...)` | analyze | An author's works, ranked. `coauthor` returns the two authors' joint output; `maximum_results` cursor-pages the full set. |
| `author_profile(author)` | analyze | Full OpenAlex author record: topics (with subfield/field hierarchy), concepts, summary_stats (h, i10, 2yr), and the complete affiliation list annotated with year ranges. Richer than the summary returned by `find_authors`/`coauthors`. Feed its output fields into `author_works`, `coauthors`, or raw analysis. |

| `book_fulltext(isbn, download=...)` | read | Acquire a **book** PDF by ISBN from Anna's Archive (member fast tier, then the keyless slow tier via FlareSolverr); `download=True` saves it and returns `pdf_path`, to attach to a Zotero `book` item. |
| `webpage_snapshot(url, out_path=...)` | read | Save a **webpage** artifact — a full-page PDF rendered with headless Chromium (Playwright; raw HTML snapshot only if the browser is unavailable) — and return its `path`, to attach to a Zotero `webpage` item. |
| `zotero_save(papers, ...)` | zotero | One-call pipeline for a **list** of paper ids/records: dedup by DOI → parallel CrossRef + PDF download → batched item create → parallel PDF attach. The default way to add papers. |
| `zotero_create(items)` · `zotero_update(updates)` · `zotero_delete(keys)` | zotero | Low-level batched item CRUD ($\le 50$ objects/request) over the Zotero Web API. `update`/`delete` take the item `key`; `update` is PATCH-semantics, every field settable at once. |
| `zotero_attach(attachments)` | zotero | Upload a list of PDFs as `imported_file` attachments under their parent items, in parallel. |
| `zotero_items(query=..., tag=..., collection=..., subcollections=..., limit=..., full=...)` | zotero | Read the library — full list (no `query`) or quicksearch, optionally scoped to one `collection` (by key **or** name; `subcollections=True` recurses the tree). Compact `{key, version, doi, title, item_type}` dicts, or the complete editable JSON with `full=True`. |
| `zotero_collections(query=...)` | zotero | List collections (all, or name-filtered) to find a collection's `key` and its place in the tree — `{key, name, parent, item_count, subcollection_count, path}`. Feed a `key`/name to `zotero_items(collection=...)`. |
| `zotero_get(keys, children=...)` | zotero | Fetch the complete data for specific item key(s) — every field, plus child notes/attachments with `children=True`. Batched: a list of keys fetches in parallel. |
| `obsidian_create(zotero_key)` | obsidian | Create `vault/{zotero_key}.md` if it does not exist: YAML frontmatter (doi, zotero_key), H1 title, abstract, and an empty **Comments** section where the user writes their own notes in Obsidian. Idempotent — skips existing files. PDF annotations are not written here; fetch them with `zotero_get(key, children=True)`. |
| `obsidian_read(zotero_key)` | obsidian | Return `{"path", "content"}` — the raw file text so you can read the user's own comments written in Obsidian. For PDF annotations (highlights made in the PDF reader) call `zotero_get(key, children=True)`; for the PDF itself pass the Zotero storage path to the LLM directly. |

The `zotero_*` functions read `ZOTERO_API_KEY` / `ZOTERO_LIBRARY_ID` / `ZOTERO_LIBRARY_TYPE` from the environment or a project `.env`; every read and write goes through the Zotero **Web API** (`api.zotero.org`) — including reads, even though Zotero's faster local API exists, because that local API is read-only (see the Zotero section of `references/sources.md`).

## Interface contract — uniform inputs and outputs

Every function follows one contract, so they can be treated uniformly and composed without surprises:

- **Input — scalar or list.** Pass the primary argument (query / paper id / author / item / key) as a single value, or as a **list** to batch; a list always fans out concurrently.
- **Output — always a dict with `meta`.** No function returns a bare list or scalar. `meta.operation` names the function; list-producing calls also carry `meta.count`.
- **List payload under `results`, single object under `result`.** `search`, `facets`, `find_authors`, `coauthors`, `author_works`, `citations`, `similar`, `zotero_items`, and every batched call put their list under `results`; `lookup` and a scalar `zotero_get` put the single object under `result`. (`fulltext` and `figures` additionally expose their file/route fields directly — `pdf_path`/`routes`, `images`/`workdir`.)
- **Batched calls (list input) → `{"meta": {operation, batch: true, count, ok, failed}, "results": [...]}`** in input order. A per-item failure is captured in place as `{"_error": "<message>", "input": <the input>}` rather than raising, so one bad item never sinks the batch — check `meta.failed` and surface the `_error` entries.
- **Zotero writes** (`zotero_create` / `zotero_update` / `zotero_delete` / `zotero_attach`) return `{"meta": {operation, count, ok, failed, ...}, "results": [...], ...}`, where `results` holds the per-item success entries (created/updated `{index, key}`, deleted keys, or attachment outcomes) with `failed` / `unchanged` / `library_version` alongside. `zotero_save` returns the richer `{meta, created, skipped, attachments, create_failures, errors, library_version}`.

## Composability — the records carry ids

The functions chain because every result record carries `ids` (`doi`, `arxiv`, `pmid`, `pmcid`, `openalex`). Take an id from any result and pass it to any id-taking function. `references/layers.mmd` sketches the id flow; there is no required order.

## Blending the sources into an enriched picture

The scholar functions are one of three complementary information sources; together they close the loop. The scholarly APIs give **breadth** (everything published), Zotero gives **depth and memory** (the user's curated, full-text library), and Claude Code gives **comprehension** (reading the actual document). Use them as a pipeline:

0. **Library first (Zotero, via the `zotero_*` functions).** Before discovering anything new, **always fetch what the user already has** — `zotero_items(query=...)` for a quicksearch on the topic, or `zotero_items()` for the full list. Reuse those records and DOIs, seed the analysis below from them, and only reach out to the scholarly APIs for what's missing. This is the mandatory first step of every task.
1. **Discover & analyze (scholar functions).** `search`/`citations`/`similar`/`facets`/`coauthors` build the map — what exists, what's influential, who works with whom.
2. **Acquire (the `fulltext` function → file).** `fulltext(paper_id, download=True, out_path=...)` walks the open-access ladder, then Sci-Hub, then the two Anna's Archive rungs (member API and keyless slow tier — for papers past Sci-Hub's 2021 freeze, when enabled via `ANNAS_SECRET_KEY` / `FLARESOLVERR_URL`; the slow tier is a reliable backstop but takes minutes per paper — see `references/sources.md`), saves the PDF where you choose, and returns citation metadata in `paper`.
3. **Keep (Zotero, via the `zotero_*` functions) — every save is a FULL citation PLUS the PDF, no exceptions.** A saved record must always end up with **(a)** complete bibliographic metadata — title, every author, journal, year, volume, issue, pages, DOI, ISSN, URL, language, abstract — **and (b)** the attached PDF whenever one could be retrieved. All Zotero access goes through the **Web API** via these `zotero_*` functions, using `ZOTERO_API_KEY` / `ZOTERO_LIBRARY_ID` / `ZOTERO_LIBRARY_TYPE` from the environment or a project `.env`. The one-call way to do all of this for a whole list at once is `zotero_save`:
   - **Pass a list of paper ids and/or records.** `zotero_save(["10.x", "10.y", record, ...], collections=[...], tags=[...])` runs the entire pipeline batched: resolve ids → **dedup by DOI** against the library (so re-running never double-adds) → fetch CrossRef bib fields **and** download the best PDF for each new paper in parallel (open-access ladder, then Sci-Hub, then Anna's Archive) → create the `journalArticle` items in chunks of 50 with every field populated → upload each PDF as an attachment in parallel. It returns `created`, `skipped` (the dedup hits, with their existing keys), `attachments`, and any per-paper `errors` — **relay the skipped and errored ones to the user.**
   - **`download` and `dedup` are on by default.** A closed-access paper with no retrievable PDF still lands as a complete metadata-only record (its `has_pdf` is `false`) — say so when it happens. Pass `dedup=False` only to force re-adding a paper that already exists.
   - **Drop to the primitives when you need finer control.** `zotero_items()` to read/inspect or build your own dedup set; `zotero_create(items)` / `zotero_update(updates)` / `zotero_delete(keys)` for batched CRUD on hand-built editable-JSON items ($\le 50$ per request, every field settable at once); `zotero_attach([{parent_key, pdf_path}])` to upload PDFs under existing items. `update`/`delete` take the item `key`; `update` is PATCH-semantics, so only the fields you pass change. Item JSON uses Zotero field names (`itemType`, `publicationTitle`, `creators`, `DOI`, `ISSN`, `abstractNote`, `tags: [{"tag": ...}]`, `collections: ["<key>"]`).
   - **No read-back needed to verify a write.** Every write function returns the created/updated keys and per-item success/failure directly, so author each field deterministically (CrossRef + abstract) and trust the returned status — there is no separate read-back or semantic-index step.
4. **Read (Claude Code).** Read the `pdf_path` directly — Claude Code renders the PDF visually, so you see figures, equations, and tables in context. Use `figures(...)` when you want the embedded figures pulled out on their own.
5. **Search your own corpus (Zotero functions).** `zotero_items(query=..., tag=..., item_type=...)["results"]` runs Zotero's quicksearch over the library metadata (title/creator/year, or everything) and returns compact records for dedup or inspection (`full=True` for complete data); `zotero_get(keys, children=True)` fetches the full data and child attachments for specific keys. This is metadata/quicksearch only — body-text semantic search over the library is not part of these Web-API functions.

Cross-pollinate both ways: a DOI from a Zotero item (`zotero_items`) seeds literature-search analysis (`citations`, `coauthors`, `similar`), and literature-search discovery feeds new PDFs back into the library via `zotero_save`. The only requirement is that the Zotero Web API credentials (`ZOTERO_API_KEY` / `ZOTERO_LIBRARY_ID` / `ZOTERO_LIBRARY_TYPE`) are present in the environment or a project `.env` — no Zotero desktop app or external server is needed.

## Backing up the library

Back up from the Zotero **desktop client**, not this package: File → Export Library → format **Zotero RDF**, ticking "Export Files" and "Export Notes" to include attachments, notes, and annotations; restore with File → Import. The Web API these functions use **cannot import RDF** (item writes are JSON-only), so a faithful files-and-annotations round-trip cannot be automated here — it is a deliberate manual desktop operation. Do not git-track Zotero's live data directory (`~/Zotero`): `zotero.sqlite` is constantly-rewritten binary and `storage/` holds large binary PDFs.

## Working principles

- **Reasoning about a paper uses three separate calls, not one.** The full context is: (1) `obsidian_read(key)` for the user's own comments written in Obsidian; (2) `zotero_get(key, children=True)` for the PDF annotations (highlights made in the PDF reader); (3) the PDF path from Zotero storage, passed directly to the LLM to read. These are distinct things — never conflate the user's Obsidian comments with PDF annotations.
- **Library first — always check Zotero before anything else.** Before any search, lookup, download, or save, **first fetch what the user already has in their library** with `zotero_items(query=...)` (or `zotero_items()` for the full list). Start every task this way: see what is already collected, reuse those records and their DOIs, and only then go out to the scholarly APIs for what's missing. This avoids re-discovering and double-adding papers the user already owns, seeds analysis (`citations`/`similar`/`coauthors`) from the existing corpus, and grounds every answer in the user's own curated memory first. Tell the user what was already in the library versus what is new.
- **Search broad by default.** Leave `work_type`, `open_access`, and the year window unset unless the user asks to narrow — the fan-out should span preprints, reviews, conference papers, and journal articles. Narrowing risks dropping relevant findings.
- **Report every warning and unexpected outcome — never silently ignore them.** Two channels carry them, and the user sees neither unless you relay it. **(1) Logged warnings** — the engine emits a `logger.warning` for every narrowing filter that could exclude papers (open-access, type, year window, per-source cap, sources not consulted, sources that failed) and every fallback (e.g. Semantic Scholar → OpenAlex). These do **not** appear in the returned dict, so call `scholar.configure_logging()` at the top of the script; the warnings then stream to stderr (and a temp log file), and `uv run` surfaces that stderr to you — read it after the run and relay what it says. **(2) Structured failure fields** in the returned dicts: a batched call's per-item `{"_error": ...}` entries (counted in `meta.failed`); and the Zotero results' `errors`, `skipped` (dedup hits, with the existing keys), `create_failures`, attachment `ok: false`, and `has_pdf: false` (a closed-access paper saved as metadata only, no PDF). After any operation, inspect these and tell the user what was excluded, skipped, failed, or only partially done — and, when it matters, why. If anything behaves unexpectedly — a source returns nothing, a count looks wrong, a write partially fails, a result is empty where you expected hits — say so plainly instead of presenting a clean-looking result that hides it.
- **Go to layer 3 only for the papers that matter.** Download (`fulltext(..., download=True)`) and read the few papers the user actually needs; abstract-level reasoning is often enough. Read the PDF directly so you see figures and equations in context.
- **Cite everything.** Title, authors, year, venue, citation count, DOI/URL, and a download link with open-access status when one exists. Say when only an abstract — not full text — backed a claim, and never invent content you could not retrieve.
- **Don't tag by default.** Leave `tags` unset on `zotero_save` / `zotero_create` unless the user explicitly asks for a specific tag — stray tags accumulate and make the library messy and confusing. The functions add tags only when you pass them, so simply omit the argument.
- **Complete the metadata — every item, every field, abstract included.** A Zotero record is only as useful as it is complete, and `zotero_save` can leave gaps (a closed-access paper with no CrossRef record, a feed missing the abstract, volume/issue/pages/ISSN/language not populated). So treat metadata completeness as a first-class task: (a) on every save, author the full field set — title, all creators, `publicationTitle`, year/date, volume, issue, pages, DOI, ISSN, url, language, and `abstractNote`; (b) periodically **sweep the whole library for missing metadata** — read every item with `zotero_items()` + `zotero_get(keys)`, flag empty fields (especially `abstractNote`), and enrich them. Enrich by fetching the authoritative sources by DOI: **CrossRef** (`api.crossref.org/works/<doi>`) for bibliographic fields and a publisher abstract, and **OpenAlex** (`/works/doi:<doi>`) for the abstract (reconstruct `abstract_inverted_index`) and `biblio` volume/issue/pages — take whichever abstract is more complete. Fill only the empty fields (PATCH via `zotero_update`, never clobber good data). **When an abstract needs cleaning, read it and rewrite it by hand** — judge what is actually wrong and fix it faithfully, rather than running brittle regex/string transforms, which mangle scientific text (they split `C₂H₂Cl₂` into "C 2 H 2 Cl 2", leave spaced subscripts like "K ₃ H(SO ₄ ) ₂", and miss mixed cases). Strip JATS/HTML markup, drop stray leading "Abstract"/"ABSTRACT", and render all math as UTF-8 — Unicode sub/superscripts (`H₂`, `C₃N₄`, `H₅O₂⁺`, `10⁸`, `10⁻⁹`) and symbols (`≤ ≥ ≈ × ± − σ π Δ`), never LaTeX. Preserve the wording verbatim; only fix formatting. If an abstract is **truncated or missing** — it starts mid-sentence (a lost opening), or is a one-line teaser — fetch the complete text from the publisher landing page (follow the DOI; e.g. RSC redirects `doi.org` → `xlink.rsc.org` → `pubs.rsc.org`) rather than inventing it. Where no abstract exists anywhere (some older papers genuinely have none), note that instead of fabricating one. **Attachments apply to every item type, not just journal articles:** a `book` item should carry its PDF — fetch by ISBN with `book_fulltext(isbn, download=True)` (Anna's Archive, the books shadow library, where textbooks — unlike post-2021 papers — are usually available) — and a `webpage` item its saved artifact from `webpage_snapshot(url)` (a full-page PDF rendered with headless Chromium via Playwright); attach either to its parent with `zotero_attach`. A saved item is only complete once its artifact is attached, whatever its type.
- **Verify, don't trust stored facts.** Treat anything you find — in this skill and its references, in CLAUDE.md, in the Zotero library, in prior results, or in your own memory — as possibly wrong or outdated. Confirm it against the live source (the scholarly APIs, the actual PDF, the current library) before relying on it or reporting it as true. A cached note is a lead to check, not ground truth.
- **Never use emojis.** Not in chat responses, tables, lists, saved Zotero data, collection or tag names, code, or commit messages — anywhere.
- **Write Zotero math and formulas in plain Unicode (UTF-8), not LaTeX — because Zotero's fields do not render LaTeX.** LaTeX is permitted project-wide, but Zotero's title/abstract/note fields and this terminal display raw `$...$` markup instead of typeset math, so for anything that lands there — saved Zotero data (item titles, `abstractNote`, notes, any other text), chat responses, terminal tables — Unicode is the form that actually renders. When saving or editing a Zotero item whose title or abstract contains math (chemical formulas like C₃N₄ / H₂, Greek like εₚ / Γ, relations like ≤), write the Unicode glyphs directly. When a source feed (CrossRef, OpenAlex, arXiv) returns a title/abstract containing LaTeX, normalize it to Unicode on the way in. (LaTeX is the right form only where it typesets — never in Zotero; charts render math through the `data-visualization` skill, not here.) Ordinary punctuation (dashes, separators) is not math and stays as-is.
- **Scope a read to a collection when the user means a curated subset.** `zotero_collections(query=...)` finds the collection's key by name; `zotero_items(collection=<key-or-name>, query=..., subcollections=...)` then reads (and quicksearches within) just that collection — the right move for "what's in my onboarding list" or any question about a specific shelf rather than the whole library.
- **Always pull abstracts and topics, not just titles.** A title is a lossy summary — judging relevance, themes, or importance from titles alone silently drops the real point of a paper and mis-weights whole research lines (a methods paper and its application can look identical from the title). For any analysis, ranking, or summary, fetch the **abstract** (it carries the actual claim, method, and finding) and the **topic/concept tags** (the authoritative subject classification — on the OpenAlex *author* record for a person, and queryable via `facets(query, by="topic")` for a body of work). Read those before forming a conclusion, and cite from them — so nothing important is missed because it never surfaced in a title.
- **Actually read what you fetch — retrieval is not comprehension.** Fetching a field is worthless unless you then *attend to its content* in your reasoning, and the easy failure is to pull a rich payload (abstracts, `topics`/`x_concepts`, citation contexts, `summary_stats`, the logged warnings, the structured failure fields, a downloaded PDF) and then reason only off the title, the count, or your prior assumption — letting everything you just retrieved go unread. Treat every field you requested as something you are obligated to consume: open the dict and read the abstract text, the topic tags, the per-item `_error` entries, the `skipped`/`has_pdf` flags, the stderr warnings, the actual PDF pages — and let what they *say* drive the conclusion, the ranking, and the wording you report. If you fetched it, use it or say why you set it aside; never pull a payload, print it, and then answer as if it weren't there. Concretely: when you `print(json.dumps(...))` a result, that JSON is input you must read back before concluding — not a formality logged and skipped. A claim must be grounded in the content you read, not in the fact that a call returned successfully.
- **Visualize bibliometric results through the `data-visualization` skill — never hand-rolled markup.** Any chart, plot, timeline, or heatmap of bibliometric results is drawn by the separate **`data-visualization` skill**, which is the sole authority on how to visualize. Snapshot the `scholar` data you want to plot into that skill's `data.json` and let it draw. Do not embed chart doctrine here.
- **Use both lists and tables — they complement each other.** Scholarly answers are usually records with repeating fields — papers (title, year, venue, citations, DOI, OA status), authors (name, affiliation, h-index, topics), themes (area, representative work, era). Give the **list** for the fine detail: the nuance, caveats, comments, and reasoning that don't fit in a cell — what a paper actually argues, why it matters, what to watch for. Then add a **table on top** as an at-a-glance layer: it aligns the shared fields, makes counts and citations scannable, and exposes gaps the prose can hide. Neither replaces the other — the table is the map, the list is the territory; for any comparison, ranking, reading list, or multi-paper/multi-author summary, offer both. Drop to prose alone only for genuinely narrative answers — a single paper, or a chain of reasoning that doesn't decompose into either form.

## Ranking

`search` ranks by an explicit `sort="citations"` or `sort="date"` when asked, otherwise by a composite of lexical relevance, log-scaled citations, recency, cross-source agreement, and venue authority. You can always re-sort any function's list yourself to fit the question — paper records (`results`) by `citations` or `year`, author records (`coauthors`/`candidates`) by `h_index` or `cited_by_count` — that is part of composing. Mind the field names: a paper's citation count lives under `citations` (not `cited_by_count`, which is the author-record field).

## Profiling an author (topics, metrics, completeness) — composable

When the question is about a person's **expertise, impact, or research themes**, do not infer it from `author_works` titles alone — those records carry **no topic/concept tags**, so a title-only reading silently misses themes and mis-weights others. The authoritative classification lives on OpenAlex's own **author** record, which `author_profile()` now surfaces directly instead of requiring a raw API fetch.

**`author_profile(author)`** returns the building blocks, not a one-size-fits-all answer. Compose them with other functions:

| Output field | Use it to... | Then compose with... |
|---|---|---|
| `topics` (subfield/field, work counts) | Discover the real expertise areas | `author_works(author, ...)` to name representative papers and citation counts under each topic |
| `summary_stats` (h, i10, 2yr mean) + `cited_by_count` | Quote impact metrics without recomputing | `coauthors(author)` for collaborator prominence |
| `affiliations` (with year ranges) + `display_name_alternatives` | Understand career arc and spot merge artifacts | Cross-check against the `affiliations.years` ranges for off-field or pre-career outliers |
| `works_count` | Completeness check vs what `author_works()` returned | Pass `maximum_results=N` to `author_works()` if fewer came back |

**Workflow:**

1. **`author_profile(author)`** — topics, concepts, stats, affiliations.
2. **Cross-check `works_count`** from the profile against `author_works()` return count. If fewer, raise `maximum_results`.
3. **Name representative papers** under each topic by feeding the author id into `author_works(author, sort="citations")`.

Stay skeptical of the merge: OpenAlex sometimes folds a stranger's paper into an author. Sweep the works for **off-field or pre-career outliers** (a lone dentistry paper under a computational chemist, a publication dated years before the real career began), exclude them, and flag the exclusion to the user. More broadly, treat every one of these fields as a thread to pull — cross-check the topics against the venues, the affiliations against the date ranges, the metrics against the citation distribution — and follow whatever the data invites rather than stopping at the first fetch.

## Inherent limits, and how to navigate them

Limits of the underlying APIs, not missing code. Work around them, and tell the user when one applies.

- **No full-text body search.** The public APIs search title/abstract/metadata, not the PDF body, and `zotero_items` only quicksearches your library's metadata. For one paper, `fulltext(download=True)` and read the PDF directly.
- **No unified complex boolean.** `query` is one free-text string per source. Run several narrower searches and merge, or use OpenAlex structure via `facets`.
- **Author name ambiguity.** `coauthors`/`author_works` resolve the top match; for a common name, `find_authors` first and pass the chosen OpenAlex id.
- **Citation-sort drift.** `sort="citations"` overrides relevance, so a broad query can surface off-topic mega-cited papers. Use it for impact, not topicality, and re-read the titles.
- **Shallow pagination.** Only the first `limit` per source. Raise `limit`, or page by repeated narrowed queries; use `facets` to size the space first.
- **Scope is scholarly literature.** Not patents, trial registries, datasets, or grey literature.
- **Citation counts disagree across sources.** The merged record keeps the maximum; treat it as approximate and cross-check with `citations`.
- **Full text may not exist.** When `fulltext(download=True)` returns no routes and `pdf_path` is null even after Sci-Hub and the Anna's Archive rungs, only the abstract is available — say so. Sci-Hub can also be blocked or unreachable on a given network, and the Anna's rungs are off unless `ANNAS_SECRET_KEY` / `FLARESOLVERR_URL` are configured.
